# metrics

Metrics on the OpenTelemetry API (`MetricsService`), exported over OTLP by whichever MeterProvider is registered globally. There is no scrape route.

- **Where they go:** with Nestrix on ([core/observability](../observability/README.md)), Nestrix registers a provider and exports to `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`, else `OTEL_EXPORTER_OTLP_ENDPOINT` plus `/v1/metrics`. The Nestrix server (0.11.0 or later) stores them with `NESTRIX_METRICS=all` (`pnpm traces:up` sets it) and charts them on its Metrics page; for Prometheus, an OpenTelemetry Collector's exporter or remote write keeps the names below. NestJS Observe registers no provider, so with Observe on these metrics are not exported. With neither, they cost nothing.
- **What is here:** requests in flight (`http.server.active_requests`), calls to `@Deprecated()` routes by route pattern (`deprecated_route_calls`), the database pool and its use (`db_pool_connections{state}`, `db_pool_max_connections`, `db_connection_acquire_duration_seconds`, `db_query_duration_seconds` by operation, `db_failures`, `db_last_failure_timestamp_seconds` and `db_incidents`: `database_busy` no connection in time, `database_timeout` a cancelled statement, `slow_query` over 1 s; when the database module is there), refused telemetry uploads (`telemetry_rejected{target,status}`), gauge reads that failed (`metric_read_failures{metric}`) and V8's heap limit (`nodejs_heap_size_limit_bytes`).
- **Nestrix's own:** request durations (`http.server.request.duration`, by `http.request.method`, `http.route` and `http.response.status_code`), CPU, memory, heap and event-loop delay. They are not recorded twice here.
- **Names:** a counter has no `_total` (`mail_sent`); the Prometheus translation adds it back (`mail_sent_total`), and a `_seconds` or `_bytes` name carries its unit (`s`, `By`), so the Prometheus names stay as they were.
- **Your own metrics**, in your own module's folder: inject `MetricsService` (the module is global). `metrics.counter(name, { description }, zeros)` (`zeros`: the series that start at 0, for an alert's `increase()`) and `metrics.histogram(name, { description, unit, advice })` return OpenTelemetry instruments (`add()`, `record()`). A value read at collection time (queue depth, lag): `metrics.collect(name, description, () => [{ labels, value }], unit)`. A read that fails or takes over 2 s is logged and counted in `metric_read_failures{metric}`; the gauge keeps its last value (cumulative export), so alert on that counter, not on the gauge going away.
- **Late provider:** the OpenTelemetry API has no proxy provider (a meter taken before one is registered stays a no-op), and Nestrix registers its provider a moment after boot. `MetricsService` remakes its instruments whenever the global provider changes: checked at each record, and every 5 s for the gauges.
- **Tests:** `recordMetrics()` (`test/metrics.ts`) registers an in-memory provider; call it before the app boots and `read(name)` the points.
- Always there: core is never removed ([apps/api/AGENTS.md](../../../AGENTS.md), "Folders").
